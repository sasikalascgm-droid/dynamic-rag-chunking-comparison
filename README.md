
# Dynamic RAG-Based PDF Question Answering System

## 1. Project Overview

Dynamic RAG (Retrieval-Augmented Generation) is a Python project that allows users to ask questions about the contents of a PDF document.

The system retrieves relevant text chunks from a PDF and uses a locally running Large Language Model (LLM) to generate answers based on the retrieved context.

This project uses a Python interview questions PDF as its knowledge source.

The project also compares different chunk sizes to understand how chunking affects retrieval.

## 2. Objectives

- Build a PDF-based question-answering system using RAG.
- Extract text from a PDF document.
- Split extracted text into meaningful chunks.
- Generate embeddings for the chunks.
- Store and retrieve embeddings using ChromaDB.
- Generate answers using a local Ollama model.
- Expose the question-answering functionality through FastAPI.
- Compare small, medium, and large chunking strategies.
- Reduce answers based on information outside the provided PDF context.

## 3. Features

- PDF text extraction.
- Section-aware text chunking.
- Embedding generation using Sentence Transformers.
- Vector storage and similarity search using ChromaDB.
- Local LLM integration using Ollama.
- FastAPI endpoint for asking questions.
- Interactive terminal chatbot.
- Single-question terminal script.
- Chunking comparison and retrieval evaluation.
- Shared Ollama client to avoid duplicate HTTP request code.
- Graceful handling of missing or empty collections.

## 10. Chunking Strategies

The project compares three chunking configurations.

| Strategy | Chunk Size | Overlap |
|---|---:|---:|
| Small | 500 characters | 50 characters |
| Medium | 1000 characters | 200 characters |
| Large | 1500 characters | 300 characters |

The chunking script attempts to preserve question and paragraph boundaries while creating chunks.

### Why Compare Chunk Sizes?

- Small chunks can provide more focused context.
- Medium chunks can preserve more surrounding information.
- Large chunks can retain more context but may retrieve less focused text.

The best configuration depends on the document and the evaluation results.

Run the comparison:

```powershell
.\venv\Scripts\python.exe compare_chunking.py
```

The results are saved to:

```text
chunking_results.txt
```

The evaluation includes keyword-based retrieval checks and distance measurements. These metrics are useful for comparison but do not guarantee answer correctness.

## 12. API Endpoint

### POST /ask

This endpoint accepts a question and returns an answer generated using retrieved PDF context.

Example request:

```json
{
  "question": "What is a Python dictionary?"
}
```

Example response:

```json
{
  "question": "What is a Python dictionary?",
  "answer": "A Python dictionary is a collection of key-value pairs."
}
```

The exact answer may vary depending on the retrieved context and the LLM response.

### Request Validation

An empty question returns HTTP 400.

If the required ChromaDB collection is missing or empty, the endpoint returns HTTP 503 with an explanatory message.

If Ollama cannot be reached, the API returns an appropriate error response.

## 17. Shared Ollama Client

The project uses `ollama_client.py` to centralize the Ollama HTTP request logic.

The shared function is:

```python
generate_answer(prompt)
```

It sends the prompt to Ollama and returns the generated answer.

The shared client is used by:

- `main.py`
- `ask_pdf.py`
- `rag_chat.py`

This avoids repeating the same request-handling code across multiple files.

The shared module also handles common errors, including connection failures, HTTP errors, invalid JSON, and empty responses.

## 18. RAG Workflow

The project follows this workflow:

1. Load the PDF document.
2. Extract text from the PDF.
3. Detect question and paragraph sections.
4. Split the text into chunks.
5. Generate embeddings for each chunk.
6. Store embeddings and text in ChromaDB.
7. Receive a user question.
8. Generate an embedding for the question.
9. Retrieve the most relevant chunks.
10. Build a prompt containing the retrieved context.
11. Send the prompt to Ollama.
12. Return the generated answer.

## 19. Error Handling

The project handles several common situations.

| Situation | Expected behavior |
|---|---|
| Empty question | Return a validation error |
| Missing collection | Explain that database preparation is required |
| Empty collection | Explain that the database must be rebuilt |
| Ollama unavailable | Return a connection error |
| Invalid Ollama response | Return a response error |
| Information unavailable in context | Ask the model to report that the answer was not found |


Check the installation:


Check that the terminal is in the project root and run:

```powershell
.\venv\Scripts\python.exe -m uvicorn main:app --reload
```

### Problem: PDF File Not Found

Verify that the PDF exists at:

```text
data/Python-Interview-Questions.pdf
```

### Problem: Answers Are Not Relevant

Inspect retrieved chunks using `query.py`, then review the chunking strategy, retrieved context, and prompt.

## 21. Limitations

- The system depends on the text that can be extracted from the PDF.
- Scanned PDFs may require OCR, which is not currently included.
- Retrieval quality depends on the embedding model, chunking, and document structure.
- The LLM can still produce unsupported answers despite strict prompt instructions.
- The project uses a local Ollama model, so generation speed depends on the available hardware.
- Keyword-based retrieval evaluation is only a basic measure of retrieval quality.
